动机 为什么要分离

改造前的核心矛盾在于：攻击代码直接在 Java 里修改数据库字段，攻击方与检测方在同一个进程、同一个对象上操作——这不叫「攻击和检测」，这叫「左手打右手」。

// 改造前：攻击直接修改内存对象，检测器「知道」哪架飞机被攻击 triggerAttack() → victim.setLatitude(xxx) → aircraftRepo.save() ↓ SecurityCheckService.check(msg, victim) // 检查同一个被修改的对象
核心矛盾：攻击先 victim.setStatus("异常") 再让检测器去查——「先射箭再画靶」。检测器拿到的不是「信号」，而是「已经被标记过的对象」。

原则 改造后的三段式信号层

  • 正常仿真只产生正常报文 —— SimulationService 不再设置任何飞机 status 为「异常」
  • 攻击注入器只写报文流 —— 不能直接改 Aircraft 对象，只能像真实攻击者一样构造恶意 hex
  • 安全检测只读报文流 —— 不知道哪些是攻击，只用算法判断
  • source 字段事后对照 —— 报文带 NORMAL / INJECTED 标记，检测完成后才用它算检出率/误报率

证据一 攻击注入器不修改 Aircraft 对象

新增 AttackInjector。位置欺骗攻击只 读取 受害飞机的字段用于构造恶意报文，从不 调用 setLatitude / setStatus / aircraftRepo.save：

// 位置欺骗：瞬间偏移约 250-500km，但只写报文，不改飞机对象 private AdsbMessage injectPositionSpoof(Aircraft victim) { double newLat = victim.getLatitude() + (RNG.nextDouble() - 0.5) * 5; double newLon = victim.getLongitude() + (RNG.nextDouble() - 0.5) * 5; return messageFactory.buildMessage(victim.getIcao(), victim.getAltitude(), newLat, newLon, victim.getSpeed(), victim.getHeading(), "INJECTED"); }

注入完成后统一写入报文总线并交给纯报文检测，全程不触碰 Aircraft 实体：

messageRepo.save(msg); // 写入报文总线，source=INJECTED securityCheckService.check(msg); // 交给纯报文检测

证据二 检测服务只读报文、不读 source 做判断

SecurityCheckService 的检测方法签名从 check(msg, aircraft) 收敛为 check(AdsbMessage msg)，不再接收攻击方对象。检测分支只读报文字段：

public void check(AdsbMessage msg) { ... // 1. CRC 校验失败 —— 判断只依赖报文自身字段 if (msg.getCrcValid() != null && !msg.getCrcValid()) { detected = true; createAlert("CRC校验失败", "红色", "...", msg); } ... }

source 字段只在 检测全部完成后 才被读取，且仅用于统计——不参与任何「是否告警」的判断：

// 事后对照验证（检测完成后才读 source，仅统计用） if ("INJECTED".equals(msg.getSource())) { injectedChecked.incrementAndGet(); if (detected) truePositives.incrementAndGet(); }

证据三 正常通道只产 NORMAL 报文

SimulationService.tick() 中，正常仿真只生成 source=NORMAL 的报文，已彻底移除攻击逻辑与状态污染：

// 每 tick 生成一条【正常】ADS-B 报文 AdsbMessage msg = messageFactory.buildMessage( ac.getIcao(), ac.getAltitude(), ac.getLatitude(), ac.getLongitude(), ac.getSpeed(), ac.getHeading(), "NORMAL" ); messageRepo.save(msg); securityCheckService.check(msg); // 正常报文同样走纯报文检测

证据四 报文实体带 source 标记

AdsbMessage 与 SecurityAlert 均新增 source 字段，作为事后统计的「对照标签」：

// AdsbMessage.java @Column(length = 10, nullable = false) @Builder.Default private String source = "NORMAL"; // NORMAL / INJECTED

结论 分离是否真的达成

达成。 攻击端（AttackInjector）与检测端（SecurityCheckService）之间不再共享任何可变内存对象：攻击只向 adsb_message 报文总线写入恶意 hex，检测只从报文流中读取并做算法判断。实测攻击后飞机真实坐标位移 0.0 km，检出率 100%、误报率 0.0%。系统已从「左手打右手的 Java 程序」升级为「可验证检测算法的安全仿真平台」。
