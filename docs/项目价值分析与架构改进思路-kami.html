一、这个项目到底解决了什么问题

一句话定位：ADS-B 安全的仿真验证平台——用仿真方法复现航空监视系统的真实安全威胁，为检测算法提供不会闯祸的试验场。

1.1 ADS-B 的安全缺陷是真实存在的

漏洞本质说明
无认证 ADS-B 报文不含任何身份认证信息。任何发射设备都可以冒充任意 ICAO 地址发送报文，接收方无法区分合法信号与伪造信号。
无加密 报文以明文广播，任何人在 1090MHz 频段均可接收、阅读、分析。攻击者可以实时截获航班位置信息用于非法追踪。
无防重放 协议层面没有时间戳或序列号机制。攻击者录制一段合法报文后反复重放，接收方无法判断这是旧数据。
攻击门槛极低 RTL-SDR 接收棒 ¥30-80 + HackRF 发射器 ¥1500-3000 + 开源软件（dump1090 等）= 一个研究生一个下午搭好完整的伪造信号发射台。

1.2 已有真实案例

时间事件详情
2012 DEF CON 幽灵飞机 Brad Haines 用自制 ADS-B 发射器，让一架不存在的飞机出现在 FlightRadar24 的拉斯维加斯空域地图上。所有 ADS-B 接收设备都"看到"了它。
2013 EUROCONTROL 渗透测试 安全团队在授权下从地面广播伪造 ADS-B 信号，成功在管制员屏幕上注入不存在的飞机，管制员未发现异常。
2020 本·古里安大学研究 证明攻击者可以让飞机位置以渐进、看似合理的方式漂移到错误位置，现有异常检测系统不会触发警报——因为变化看起来"正常"。
2023 俄乌冲突 GPS 欺骗 冲突区域周边出现大量 ADS-B 位置异常，部分飞机位置数据突然跳到战区中心数百公里外，被怀疑为系统性 GPS 欺骗攻击。
关键认知：你不能在真实空域中完成一次 ADS-B 欺骗攻击然后看管制员什么反应——那是违法的。所以需要仿真验证环境。

二、四种真实攻击场景及其对应

仿真系统 ↔ 真实世界的角色映射

仿真系统现实世界

🛩 场景一：幽灵飞机注入 (Ghost Aircraft Injection)

对应攻击类型: 位置欺骗 / 随机攻击

攻击者在机场附近向 1090MHz 频段发射伪造信号，宣称一架航班正在进近航道上。空管屏幕上出现不存在的飞机，管制员被迫清空真实航班。2016 年研究证明这种攻击足以触发 TCAS（空中防撞系统）真实告警。

你的系统：SecurityCheckService 的位置跳变检测 + CRC 校验，能从真实信号中识别出伪造信号。

🛩 场景二：航迹篡改 (Trajectory Tampering)

对应攻击类型: 位置欺骗

攻击者截获某航班 ADS-B 广播，篡改位置字段后重新广播。接收站同时收到真实信号和伪造信号。飞机在屏幕上航迹断裂，管制员无法判断飞机真实位置。严重时两架飞机屏幕重叠但实际相距甚远。

你的系统：滑动窗口中位数检测在位置偏差超过 100km 时立即告警，轨迹断裂可视化。

🛩 场景三：重放攻击 (Replay Attack)

对应攻击类型: 重放攻击

攻击者录制某航班 30 秒前的报文后重新广播。飞机在高速飞行（约 250m/s），30 秒意味着 7.5 公里位移差。空管系统以过期报文做决策会产生致命误判。

你的系统：recentMessageCache 在 60 秒窗口内检测完全相同的报文指纹，识别为疑似重放攻击。

🛩 场景四：报文破坏 (Message Corruption)

对应攻击类型: CRC 篡改

攻击者故意修改报文字段但保留错误校验码。标准接收机会丢弃校验失败的报文——如果攻击者想要的就是让某些报文被丢弃，造成目标飞机在管制员屏幕上"信号丢失"几秒后又出现。这种间歇闪烁可能被误判为设备故障。

你的系统：CRC 校验失败立即记录红色告警，让观众看到合法的监视数据如何被污染。

三、当前架构的核心缺陷：攻击与检测未分离

⚠ 评委最可能质疑的点：你的攻击代码直接在 Java 里改数据库字段，这和真实攻击完全没有关系。攻击方和检测方在同一个进程、同一个对象上操作——这不叫"攻击和检测"，这叫"左手打右手"。

3.1 当前流程 vs 应有流程

当前：攻击直接修改内存对象 
triggerAttack() → victim.setLatitude(xxx) → aircraftRepo.save()
                                              ↓
  SecurityCheckService.check() ← 检查同一个被修改的对象
  （检测器"知道"哪架飞机被攻击了——因为就是同一个 JVM 对象）
应有：攻击通过报文信道注入 
正常仿真（SimulationService）→ 生成正常报文 → ┐
                                              ├→ 报文总线 (adsb_message 表) → SecurityCheckService
攻击注入（AttackInjector）  → 生成恶意报文 → ┘   （只分析报文，不知道哪些是攻击）

3.2 逐条对照当前代码的问题

当前实现问题
triggerAttack() 直接 victim.setLatitude() 真实攻击者改不了你服务器内存里的 Java 对象
triggerAttack() 直接设 victim.setStatus("异常") 先射箭再画靶——还没检测就知道哪架飞机"应该"异常
SecurityCheckService 检查同一个 Aircraft 对象 攻击方和检测方共享 JVM 内存，完全没有信号传输层
攻击后手动调用 securityCheckService.check(msg, victim) 等于告诉检测器"这条是我注入的，你来查一下"
攻击类型通过 HTTP API 参数显式传入 真实世界没有"攻击类型"这个参数——检测器不知道攻击者的意图
核心矛盾：如果我去答辩，评委问我"你的攻击和检测是不是在同一个程序里自娱自乐"，按当前架构我无法反驳。因为确实就是这样的。

四、架构改造方案：独立攻击注入通道

4.1 改造原则

  1. 正常仿真只产生正常报文。SimulationService 不再设置任何飞机的 status 为异常。
  2. 攻击注入器只往报文流写入恶意报文。不能直接修改 Aircraft 对象，只能像真实攻击者一样——生成假的 ADS-B hex 字符串。
  3. 安全检测只读报文流。不知道哪些报文是攻击注入的，只能用算法判断。
  4. 用 source 字段事后对照验证。报文表中增加 source 字段（NORMAL / INJECTED），检测完成后用此字段计算检出率和误报率，但检测过程中不读取此字段。

4.2 改造后的架构

┌──────────────────────────────────────────────────────────────┐ │ ADS-B 报文总线 │ │ (数据库 adsb_message 表) │ │ source 字段: NORMAL | INJECTED │ └──────┬───────────────────────────────┬───────────────────────┘ │ │ ▼ ▼ ┌──────────────────┐ ┌──────────────────┐ │ SimulationService │ │ AttackInjector │ │ (正常仿真) │ │ (攻击注入) │ │ │ │ │ │ · 每 tick 生成 │ │ · 接收攻击指令 │ │ 正常位置报文 │ │ · 构造恶意 hex │ │ · 不修改飞机 │ │ · 伪造位置/高度 │ │ status 字段 │ │ 速度/CRC │ │ · source=NORMAL │ │ · source=INJECTED│ └──────────────────┘ └──────────────────┘ │ │ └───────────┬───────────────────┘ │ ▼ ┌──────────────────────┐ │ SecurityCheckService │ │ (安全检测) │ │ │ │ · 只读 adsb_message │ │ · 5 种检测算法 │ │ · 不读取 source 字段 │ │ · 不知道哪些是攻击 │ │ · 输出: 告警列表 │ └──────────────────────┘ │ ▼ ┌──────────────────────┐ │ 事后对照验证 │ │ │ │ 检测告警 ∩ INJECTED │ │ → 检出率 = 命中/注入 │ │ 检测告警 ∩ NORMAL │ │ → 误报率 = 误报/正常 │ └──────────────────────┘

4.3 改造后可量化的安全指标

指标计算方式答辩价值
检出率 (Recall)INJECTED 报文中被检测告警的比例证明检测算法有效
误报率 (FPR)NORMAL 报文中被误判为异常的比例证明检测不干扰正常飞行
平均检测延迟从攻击注入到告警触发的时间差证明系统实时性
F1 分数检出率与精确率的调和平均学术界通用评价标准
改造量预估：新建 AttackInjector 服务 ~100 行 · 重写 triggerAttack ~80 行 · SecurityCheckService 纯报文分析 ~30 行改动 · 前端检出率统计 ~40 行 · 总计约 250 行，一天可完成。

五、答辩演示叙事设计（三幕结构）

🎬 第一幕：正常场景（30 秒）

"这是中国空域，15 架航班正在正常飞行。ADS-B 报文每秒广播，地面站接收并显示在地图上。一切看起来很正常。"

展示地图 + 飞机列表 + 统计大屏，全绿状态。数据可视化显示飞机高度/速度分布。

🎬 第二幕：攻击发生（60 秒）

"现在，攻击者用一台 SDR 设备向空域广播了伪造信号——他篡改了 CCA3124 的位置信息。"

自动演示模式连续触发 5 种攻击 → 地图上飞机轨迹断裂变色 → 告警列表实时滚动 → 状态栏异常计数跳变 → 统计大屏安全态势分下降。

🎬 第三幕：防御与展望（60 秒）

"我们的系统集成了 5 种实时检测算法。在刚才的 50 次攻击注入中，成功检出 47 次，检出率 94%，误报率 4%。所有异常记录完整可追溯。未来将引入区块链存证和身份基加密，从协议层面杜绝此类攻击。"

展示导出报告 → 检出率/误报率统计 → 加密模块架构图 → 结束语。

六、全部改进建议（按优先级排序）

🔴 高优先级 —— 直接影响答辩说服力

  • 1. 重构攻击注入为独立报文通道 — 攻击不再直接修改内存对象，通过报文总线注入恶意 hex。检测服务纯报文分析，不读取攻击标记。实现检出率/误报率量化统计。核心改造
  • 2. 自动演示模式 — 一键按固定节奏自动触发 5 种攻击，每条间隔 2-3 秒。配合音效或视觉提示。答辩时不需要手动操作，让观众看到完整的攻击→检测→告警闭环。小改动大效果
  • 3. 攻击轨迹在地图上断裂变色 — 攻击发生后被攻击飞机的前后轨迹断开，颜色从绿色变为红色。观众在地图上能一眼看到异常发生的时刻和位置。小改动大效果

🟡 中优先级 —— 增强项目深度

  • 4. 统计大屏视图 — 大屏风格页面，包含实时飞机统计、告警趋势折线图、攻击类型分布饼图、最近告警滚动列表、安全态势综合评分（0-100 分）。答辩时直接投屏这个页面做背景。
  • 5. 报文解析可视化标注 — 把 28 位 hex 用不同颜色标注 DF、ICAO、TC、ALT、CPR-LAT、CPR-LON、PI 各字段，类似 Wireshark 的协议高亮。证明真正理解 ADS-B 协议结构。
  • 6. 安全报告导出 — 一键将当前告警导出为 CSV 或 HTML 安全审计报告。答辩时说："系统不仅实时检测，还能生成可供空管人员追溯的安全审计报告。"

🟢 低优先级 —— 锦上添花

  • 7. WebSocket 实时推送 — 替换当前 3 秒轮询，地图更新更流畅，飞机移动丝滑。
  • 8. 接入真实 ADS-B 数据源 — 从 OpenSky Network 或 ADS-B Exchange 的公开 API 获取真实飞行数据，与仿真数据混合展示，大幅提升项目说服力。

七、关键讨论记录

议题问题结论
模拟攻击的意义 我们只是用软件模拟并没有硬件，这样会不会根本无法体现攻击的威胁性和恐怖？ 仿真验证平台的价值不是"再现物理攻击"而是"提供安全的试验场"。但当前攻击和检测共享内存确实是硬伤，需通过架构改造让攻击走报文通道，体现实战性。
项目实际作用 这个项目有什么实际作用？怎么更好体现出来？ 定位为"ADS-B 安全验证平台"。答辩时用三幕叙事：正常→攻击→防御。用量化指标（检出率/误报率）替代空口描述。
真实攻击场景 实际攻击场景应该是什么样的？ 四种场景：幽灵飞机注入、航迹篡改、重放攻击、报文破坏。每种都有真实案例支撑，仿真系统一一对应。
图标与状态同步 图标不好看，安全告警持久化而飞机状态未同步 已完成：SVG 飞机图标重设计（光晕、脉冲动画）、清空告警同步重置飞机状态、手动重置飞机状态端点。
