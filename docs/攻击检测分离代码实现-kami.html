总览 分离的物理形态：一个「信号信道」

攻击方与检测方之间没有共享任何可变内存对象，唯一的联系是报文总线（adsb_message 表）——它扮演真实世界里「1090MHz 无线信道」的角色。

攻击端 AttackInjector │ 1. 选中一架飞机，构造一条「被篡改」的恶意 hex │ 2. 只做一件事：把这条报文写入报文总线（source=INJECTED） ▼ ┌───────────────────────────────────────────┐ │ 报文总线 adsb_message 表（唯一的信号信道） │ │ 报文里只有：icao + rawHex + 高度/速度/经纬度/CRC │ └───────────────────────────────────────────┘ │ 3. 检测端只从这里「读」报文流 ▼ 检测端 SecurityCheckService │ 4. 用 5 个算法独立判断「这条报文是否异常」 │ 不读 source 字段，不知道哪条是攻击注入的 ▼ 告警列表 + 事后统计（此时才读 source 算检出率/误报率）
关键：攻击端写入报文后，没有向检测端传递「哪架飞机被攻击了」这个信息；检测端是靠「报文内容本身」推断出来的。这正对应你说的——一端先发出攻击信号，另一端再接收到并自行判断，而不是发射的那一刻检测端就知道受害者是谁。

攻击端 一、攻击代码是怎么「发射信号」的

核心类 AttackInjector。它挑选受害者、构造恶意报文、写入总线——从不修改 Aircraft 对象，也不通知检测端。

// AttackInjector.java —— 注入一次攻击 public Map<String, Object> inject(String attackType) { // 只攻击仿真飞机（有活跃报文流与检测历史） List<Aircraft> all = aircraftRepo.findBySource("SIMULATION"); if (all.isEmpty()) return Map.of("success", false, "message", "没有仿真飞机可攻击"); Aircraft victim = all.get(RNG.nextInt(all.size())); String type = attackType != null ? attackType : ATTACK_TYPES[RNG.nextInt(5)]; AdsbMessage msg = switch (type) { case "position" -> injectPositionSpoof(victim); case "altitude" -> injectAltitudeSpoof(victim); case "speed" -> injectSpeedOverrun(victim); case "crc" -> injectCrcCorruption(victim); case "replay" -> injectReplay(victim); default -> null; }; if (msg == null) return Map.of("success", false, "message", "未知攻击类型"); // ★ 攻击只「发射」一条恶意报文到报文总线，不通知检测端受害者是谁 messageRepo.save(msg); // 写入报文总线，source=INJECTED securityCheckService.check(msg); // 交给纯报文检测，检测端自行判断 return Map.of("success", true, "attackType", type, "victimIcao", victim.getIcao()); }

再看「位置欺骗」攻击：它只是用被篡改的经纬度去构造一条报文，并没有去改飞机对象。

// 位置欺骗：只构造一条「篡改后」的报文，不修改 Aircraft 对象 private AdsbMessage injectPositionSpoof(Aircraft victim) { double newLat = victim.getLatitude() + (RNG.nextDouble() - 0.5) * 5; double newLon = victim.getLongitude() + (RNG.nextDouble() - 0.5) * 5; // 用被篡改的经纬度构造报文，source 标记为 INJECTED return messageFactory.buildMessage(victim.getIcao(), victim.getAltitude(), newLat, newLon, victim.getSpeed(), victim.getHeading(), "INJECTED"); }

检测端 二、检测代码是怎么「接收并判断」的

核心类 SecurityCheckService。它的入口 check(AdsbMessage msg) 只接收一条报文，不接收任何「攻击标记」或「受害者身份」参数。

// SecurityCheckService.java —— 对一条报文做纯报文分析 public void check(AdsbMessage msg) { // ★ 只收一条报文，不接收任何“攻击标记” if (msg == null) return; String icao = msg.getIcao(); Aircraft aircraft = aircraftRepo.findByIcao(icao).orElse(null); // 仅用于标记状态 boolean detected = false; // 1. CRC 校验失败 if (msg.getCrcValid() != null && !msg.getCrcValid()) { detected = true; createAlert("CRC校验失败", "红色", "...", msg); markAbnormal(aircraft); } // 2. 速度超限 if (msg.getSpeed() != null && msg.getSpeed() > MAX_SPEED_KT) { detected = true; createAlert("速度超限", "橙色", "...", msg); markAbnormal(aircraft); } // 3. 高度异常（绝对高度超出飞行包线）…（阈值判断，略） // 4. 位置跳变：滑动窗口中位数检测（核心算法） Deque<double[]> window = positionWindows.computeIfAbsent(icao, k -> new ArrayDeque<>()); window.addLast(new double[]{msg.getLatitude(), msg.getLongitude()}); if (window.size() > WINDOW_SIZE) window.removeFirst(); if (window.size() >= 3) { // 取窗口内经纬度中位数作基准 double medianLat = 中位纬度, medianLon = 中位经度; double dist = haversineDistance(medianLat, medianLon, msg.getLatitude(), msg.getLongitude()); if (dist > MAX_DISTANCE_KM) { // 偏离中位数超 100km detected = true; createAlert("位置异常跳变", "红色", "...", msg); markAbnormal(aircraft); } } // 5. 高度突变（相邻报文对比）+ 重放检测（60秒内相同 hex）…（略） // ★ 事后对照验证：检测【完成后】才读 source，仅用于算检出率/误报率，不参与上面的判断 if ("INJECTED".equals(msg.getSource())) { injectedChecked.incrementAndGet(); if (detected) truePositives.incrementAndGet(); } else { normalChecked.incrementAndGet(); if (detected) falsePositives.incrementAndGet(); } }

注意最后一段：source 字段是在所有检测算法跑完之后才读取的，而且只用来做「检出率 / 误报率」统计——检测「这条报文是否异常」的决策过程，全程没有用到它。

对照 三、两者在代码里到底是怎么「分离」的

维度攻击端 AttackInjector检测端 SecurityCheckService
职责构造恶意报文，写入总线读报文流，判断是否异常
是否改 Aircraft否（只读受害者字段构造 hex）命中后才把状态标「异常」
接口inject(type) → 输出一条报文check(msg) ← 只接收一条报文
知不知道受害者攻击时知道（自己选的）不知道，靠算法从报文推断
读不读 source写 source=INJECTED判断时不读，事后统计才读
一句话：攻击端「只知道自己在发射什么」，检测端「只知道自己在接收什么」，两者通过报文总线这个「信道」连接，发射方不知道检测方如何判断，检测方也不知道哪条是攻击——这就是「发射 → 接收」的分离，而不是「发射即知」。

诚实说明 四、当前实现的边界

要如实说明：当前两者是同一个 JVM 进程内、通过数据库表（报文总线）传递的软件层分离，不是真实的射频/网络物理分离。也就是说：

  • ✅ 逻辑上完全分离：不同服务、无共享可变状态、检测不读 source、不接收受害者身份
  • ✅ 检测的「判断」和攻击的「发射」彼此独立，检测结果完全由报文内容决定
  • ⚠️ 物理上仍是同进程调用 check(msg)，若要模拟真实的「空中传播 + 接收」异步过程，可进一步换成消息队列 / 数据库轮询 / WebSocket 推送

对当前「安全仿真验证平台」的定位而言，这套软件层分离已经达到了「检测器不知道攻击源」的核心目标，也支撑了检出率/误报率的量化验证。
